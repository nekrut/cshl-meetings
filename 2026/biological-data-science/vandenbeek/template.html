From research code to reproducible infrastructure with Galaxy user-defined tools

Marius van den Beek1, John Chilton1, Dannon Baker2 1The Pennsylvania State University · 2Johns Hopkins University
Galaxy has thousands of tools, yet the one step you need is often missing. A UDT closes that last mile: write it, test it on real data on a production server, iterate, then graduate it to a community tool.
Try it on usegalaxy.org
Request access once at udt-signup.galaxyproject.org. No install or review per tool.

AThe gap

Research code starts as a notebook, a lab script, a published method, or AI-drafted code. Writing the first version is the easy part. To become a step you can rerun, scale up, and share, it also needs:

  • 1Interfacetyped inputs and outputs
  • 2Environmentthe exact software
  • 3Datalarge datasets, in place
  • 4Computecores, memory, GPUs
  • 5Provenancewhat ran, on what, how
  • 6Sharinga step others can reuse

On a shared Galaxy server, a new tool must also be wrapped, reviewed, and installed by an administrator: the right default for shared tools, but slow for one small step.

A user-defined tool (UDT) covers all six in about 40 lines, in your own account, with no install to wait for.

BThe last mile

3 Data6 Sharing

usegalaxy.org runs ~2,500 tools from a Tool Shed of 8,000+ repositories. What’s missing is usually one small step: a new method, an extra option, a wrapper merged but not yet installed.

Write→Run on real data→Inspect→Edit↻

Each round is a save in the tool editor, on the production server with real data.

Then graduate it to a community tool

UDT in your account→tools-iwc-lab→tools-iuc

When a UDT proves itself, wrap it as a standard tool and open a pull request to galaxyproject/tools-iwc-lab. Planemo lints and tests it in CI, then publishes it to the Tool Shed under iwc-lab. Mature wrappers graduate to tools-iuc for installation on any Galaxy server.

DSafe by construction

In the tool definition

  • Commands are templated with sandboxed JavaScript expressions that cannot reach the database or filesystem
  • A container is mandatory
  • Inputs are typed and validated before a job exists

At the site

  • Access is granted once per account
  • Routing and resource limits stay with the site (E)
Each job runs with minimal permissions and can only access its own input and output data.

ERequesting compute

The tool declares what it needs

cores_min: 32→cores 32ram_min: 8192→mem 8 GiBcuda_device_count_min: 1→gpus 1

The site’s job router (TPV) applies policy

  • Only destinations that opt in accept UDT jobs
  • GPU requests need the GPU Access role
  • Per-user pools cap a user’s total cores, memory, GPUs

Jetstream2 GPU node (NSF ACCESS)

  • Pulsar + Singularity, container required
  • 32 cores map to $GALAXY_SLOTS, plus 1 GPU

FWhat Galaxy does with it

Validate→Build form→Run in container→Record provenance→Reuse in workflows

GWhat AI agents do with UDTs

  • Galaxy Workflow Foundry gives AI agents the domain knowledge to translate external pipelines into native Galaxy workflows. When we converted nf-core/rnaseq for usegalaxy.org, every step mapped to an installed Galaxy tool except RSEM quantification, whose community wrapper was merged but not yet installed. The agent wrote an RSEM UDT so the workflow could run immediately. Its outputs matched the community wrapper’s test suite exactly.
  • Orbit, an AI assistant that plans and runs analyses on Galaxy, builds the tool when none fits. It writes a UDT, has Galaxy validate it, runs it on the real data, reads any failure, fixes and re-creates it, and carries on with the analysis. Each definition is saved with the analysis notebook, keyed to the exact tool that ran.
